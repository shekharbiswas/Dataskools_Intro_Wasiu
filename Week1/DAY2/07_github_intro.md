## 💡 So... What *Is* GitHub?

GitHub is an online platform where people **store, organize, and share files** — mostly code, but not only code.

Think of it like:
- 📦 Google Drive for technical projects  
- 📚 A public journal for your learning journey  
- 🎓 A portfolio you’ll be proud to share by the end of this course

It’s built on something called **Git**, which is like a time machine for your work
— you can track every change, go back, or share it with others.

## 🧠 Key Terms from the video

As you start using GitHub, you’ll come across a few new words. Don’t worry — you don’t need to memorize them all right away.  
Here’s what they mean in everyday language, with real-life examples.

<br>

### 📁 Repository (or “repo”)

A **repository** is just a folder — but on the internet.

It stores all your project files (code, notes, images, data), and keeps track of every change you make over time.

> Think of a repo like your course folder. Inside it, you have folders for Week 1, Week 2, and so on. Everything lives in one place.

You can create a **private** repo (just for you), or a **public** one (visible to others — great for sharing work).

<br>

### 🌿 Branch

A **branch** is like a copy of your project where you can experiment safely without changing the original.

> Imagine you're editing a recipe in your notebook. Instead of writing over the original, you copy the page and try changes on the copy. That’s a branch.

In GitHub, the main version is called `main` or `master`. You can create a new branch (e.g. `new-header`, `fix-typo`, `test-design`) and work on it separately.

<br>

### 🔀 Merge

Once your changes in a branch are done and look good, you want to **merge** them into the main version.

> Like pasting your updated recipe into the original notebook once you’re happy with it.

Merging combines your work with the main branch — so now the project is updated for everyone to see.

GitHub also shows if there are any “conflicts” — two people changing the same thing — and helps you resolve them.

There are more terminologies but we will slowly learn those.

<br>

## 🤝 How a team works on GitHub

Let’s say a team is building an app (or a data project). Here’s how GitHub keeps them organized:

1. The team has **one shared repository**
2. Each member creates their own **branch** for the task they’re working on (e.g. charts, docs, filters)
3. They **commit** (save) changes as they go, with clear messages like “added pie chart” or “fixed spelling”
4. When they’re done, they open a **pull request**: “I want to merge my changes into the main project”
5. Others **review** the pull request to check and give feedback
6. If it looks good, they **merge** the branch into `main` — and it becomes part of the final project
7. With **CI/CD**, the updated version might go live immediately!

This flow helps teams:
- Stay organized
- Avoid overwriting each other’s work
- Review and improve each other’s ideas
- Publish clean, working projects faster

> ✅ Even if you're learning solo now, knowing how teams work on GitHub prepares you for real-world collaboration.
